# 树莓派测试清单

在测试 AA 上逐条点一遍，每条做完打勾。适用版本：**1.1.0**。

群号、QQ 号都用下面的**测试值**（`100000001`、`12345671` 这类明显是编的数字），不要用真实号码，也不要把真实号码放进截图或 issue。

---

## 准备

- 按 [GUIDE](GUIDE.md) 第 2 节装好插件，第 4 节分配好权限。
- 四个**普通**测试账号 A、B、C、D：都有主角色，状态是 Member。账号 A、B、C 在下面各节里反复用到；账号 D 是一个这一小时里还没提交过任何 QQ 的新账号，只在 F 节测「限制尝试的 QQ 号」时用（次数是按账号计的）。
  **不要用超级管理员测成员功能**：超级管理员不会自动获得入群资格（GUIDE 第 4 节）。
- 一个 QQ 管理员账号（可以是你自己的账号，加进「QQ 管理」组）。
- 「模拟机器人」：树莓派上还没有 Koishi 时，用它代替机器人。
  在 AA 虚拟环境、`myauth` 目录下（GUIDE 第 2 节第 0 步）运行 `python manage.py shell`，
  粘贴 GUIDE 第 2 节第 7 步里的那段代码（从 `import json, secrets` 到 `bot("health")`），按两次回车。之后可以这样调用：

  | 调用 | 作用 |
  |---|---|
  | `bot("groups")` | 机器人看到的群 |
  | `bot("check", {"group_id": "100000001", "qqs": ["12345672"], "full_roster": True})` | 假装机器人巡检，上报这个群的**完整**名单（这里只有 `12345672`） |
  | `bot("check", {"group_id": "100000001", "qqs": ["12345671", "12345672"]})` | 查询这几个 QQ 在这个群的判定（不改名单） |
  | `bot("claim", {"qq": "12345671", "text": "QQ-XXXXXX", "group_id": "100000001"})` | 假装 QQ 12345671 带着验证码申请入群（`XXXXXX` 换成卡片上的验证码） |
  | `bot("events", {"after": 0})` | 机器人拉取事件（事件要等 10 秒以上才能拉到） |

  退出 shell 用 `exit()`；下次再用要重新粘贴。

## A. 安装

- [ ] GUIDE 第 2 节第 7 步的检查全部通过：`check` 没有 `qqbot.` 提示；`curl` 得到 `401`；`bot("health")` 得到 `200` 和 `"config_ok": true`；
      后台「Periodic tasks」里有 `qqbot_reconcile`。
- [ ] `pip show aa-qqbot` 显示 `Version: 1.1.0`。
- [ ] 「QQ 绑定」卡片内容的最下面（靠右）显示 `aa-qqbot 1.1.0`；「QQ 管理」→「设置」标题栏右边显示「插件版本：aa-qqbot 1.1.0」。
- [ ] 在 `local.py` 里临时加上 `QQBOT_AUDIT_RETENTION_DAYS = 10`，重启 AA：`python manage.py check` 显示 `qqbot.W003`；
      重新进 `python manage.py shell`、粘贴模拟机器人的代码后，`bot("health")` 的 `problems` 里有 `"qqbot.W003"`，`"config_ok"` 仍然是 `true`。
      测完删掉这一行（或改成 `365`，警告随之消失）并重启 AA。

## B. 权限和入口

- [ ] 给 Member 状态挂上「QQ 绑定 - 成员」后，A 在「服务（Services）」页看到「QQ 绑定」卡片，标签是「未启用」。
- [ ] A 的左侧菜单没有「QQ 管理」；A 直接打开 `/qqbot/manage/` 得到 403。
- [ ] 管理员的左侧菜单有「QQ 管理」，卡片底部也有「QQ 管理」按钮。
- [ ] 超级管理员（所在状态没有成员权限）打开「服务」页：卡片上方有黄色提示「你的账号没有被授予「QQ 绑定 - 成员」权限……」。
- [ ] 打开 `/qqbot/` 会自动跳到「服务」页的卡片。

## C. 管理：群和设置

- [ ] 「QQ 管理」→「QQ 群」里添加固定群 `100000001`。
- [ ] 添加身份组小群 `100000003`：不选 AA 组时保存会报错；选一个 A 不在的组后可以保存。
- [ ] 「设置」里把「换绑冷却」改成 `0`（方便下面的测试，测完改回 `24`）。
- [ ] 「操作记录」里能看到上面这些操作。
- [ ] `bot("groups")` 返回这两个群。

## D. 新成员：验证码

- [ ] A 填昵称和 QQ `12345671` 并提交：卡片显示验证码、剩余分钟数、3 步说明，以及固定群 `100000001`（看不到身份组小群）。
- [ ] 换一个浏览器登录 A：卡片提示验证码只在原来的浏览器显示；点「重新生成」后得到新码。
- [ ] 用模拟机器人 `claim`，带上卡片上的验证码：返回 `"claimed": true`，`result` 里是 `"decision": "allow"`。
      刷新后 A 的卡片变成「已启用」，显示群名片和群号。
- [ ] 同一个验证码再 `claim` 一次：返回 `"outcome": "code_used"`，`result` 里仍然是 `"decision": "allow"`。
- [ ] C 填 QQ `12345673` 拿到验证码后，用模拟机器人把 `12345673` 报进名单（`check`，`"full_roster": True`，名单里带上已有的号）：
      C 的卡片出现「检测到你已经在群里，点「重新生成」即可直接免验证」；点「重新生成」后变成「老成员免验证」。

## E. 老成员：免验证与冲突

（正式使用时，要等机器人第一次巡检成功再通知老成员绑定，见 GUIDE 第 2 节第 7 步；这里用模拟机器人代替巡检。）

- [ ] 用模拟机器人 `check`，参数 `"full_roster": True`，名单为 `["12345672"]`。
- [ ] B 填 QQ `12345672`：马上「已启用」，状态为「老成员免验证」，不出验证码。
- [ ] 管理员打开「待处理」：「最近的免验证绑定」里有 B（主角色、QQ `12345672`、所在的群）；「已绑定成员」页第 4 张统计卡片的数字是 1。
- [ ] A 在卡片里「换绑」成 `12345672`：A 和 B 的卡片都显示红色「冲突」，不显示群号；
      `check` 这个 QQ 得到 `"decision": "review"`、`"reason": "CONFLICT"`。
- [ ] 冲突期间，管理员的侧边栏「QQ 管理」和卡片上的「QQ 管理」按钮显示红色数字 `1`；打开 `/qqbot/manage/` 直接到「待处理」。
- [ ] 管理员在「待处理」里确认 B：B 变为「已验证」，A 的认领作废（A 现在没有绑定），操作记录里有记录；红色数字消失。
      后面需要 A 有绑定的步骤，先让 A 重新绑一个测试 QQ（用模拟机器人 `claim`，或把它报进名单）。C 仍然留着 D 里得到的「老成员免验证」绑定。

## F. 改昵称、换绑、解绑

- [ ] 改昵称后，卡片上的群名片跟着变；10 秒后 `bot("events", {"after": 0})` 里有这个 QQ 的 `card` 事件。
- [ ] 故意填不合法的昵称（例如超过 12 个字）：提示显示在卡片里，小表单保持展开，填过的内容还在。
- [ ] 页面过期保护（「换绑冷却」仍是 `0` 时做；用 C，它还留着 D 里的免验证绑定）：管理员在「已绑定成员」→「详情」页打开 C 的设置群名片表单，先不提交；
      用模拟机器人把另一个测试 QQ（例如 `12345675`）报进名单（`check`，`"full_roster": True`，名单里带上已有的号），让 C 在卡片里换绑成 `12345675`（老成员免验证，马上生效）；
      管理员回到还没刷新的旧页面提交群名片：提示「这个成员的 QQ 刚刚变了，页面上的信息已经过时。请重新打开页面核对后再操作。」，`12345675` 的群名片没有被改动。
- [ ] 解绑时不勾选「我确认要解除绑定」不能提交；勾选后解绑成功。
- [ ] 把「换绑冷却」改回 `24`：换绑时卡片写明「还要等 …」。
- [ ] 管理员在「已绑定成员」→「详情」里强制解绑一个人。
- [ ] 被强制解绑的人（「换绑冷却」为 `24` 时，即使之前自己解绑过）马上填另一个 QQ：不提示冷却。
- [ ] 造一个免验证绑定 → 管理员强制解绑 → 同一个人再填**同一个** QQ（仍在名单里）：拿到验证码，不是「老成员免验证」；卡片上没有「被强制解绑过」之类的字样。
- [ ] 卡片上的 QQ 打码，用一个这一小时里还没提交过 QQ 的测试账号 D（A、B 前面已经提交过几个 QQ，次数会累计；可以新建一个测试账号，或者等一小时）：
      D 填 8 位的测试 QQ `12345678`，卡片显示 `1******8`（只露第一位和最后一位）；再填 9 位的 `123456789`，卡片显示 `12*****89`（前 2 位和后 2 位）。
- [ ] 限制尝试的 QQ 号（接着上一条，还是 D）：D 再依次提交 3 个不同的 QQ（例如 `22345671` 到 `22345673`），累计 5 个不同的 QQ；然后提交第 6 个不同的 QQ（例如 `22345676`）：
      提示「一小时内尝试的不同 QQ 号太多（最多 5 个），请稍后再试。」，不管 `22345676` 是空闲还是已被别人验证。
      再提交前 5 个里的某一个：不会出现这句话（可能出现「生成验证码太频繁」，那是另一条限制：每小时最多 5 个验证码）；只改当前 QQ 的昵称也不会。
      想重做这一条，等一小时，或者让 IT 清掉 Redis 缓存里 D 的 `qqbot:qq-tries:<用户编号>`。
- [ ] 超级管理员在后台「Users」里删除一个已绑定 QQ 的用户（单个删和「Delete selected users」各一次）：不报权限错误；
      「操作记录」里各有一条「账号删除」；10 秒后 events 里各有一条这个 QQ 的 `recheck`。
- [ ] 只有 `auth | user | Can delete user` 加上确认页列出的其他删除权限（见 GUIDE 第 5 节）的 staff 账号也能删；不需要任何 QQ 绑定权限。

## I. 对账

- [ ] `python manage.py qqbot_reconcile` 显示「对账完成」，以及写出的事件数和清理的旧事件、旧验证码、旧操作记录条数（没有设置 `QQBOT_AUDIT_RETENTION_DAYS` 时，旧操作记录是 0 条）。
- [ ] 让 AA 连不上消息队列（broker）：把 `local.py` 里的 broker 地址临时改成一个不存在的端口（不要停 Redis：AA 的缓存和 session 也用它），然后重启 AA（gunicorn 和 celery 都要重启）。
      管理员在「QQ 管理」→「设置」里改群名片格式并保存：页面马上保存成功、不会卡住；AA 日志里有一条 `qqbot: could not queue reconcile` 错误。
      测完把 broker 地址改回去，再重启一次 AA（gunicorn 和 celery），然后运行 `python manage.py qqbot_reconcile`，群名片才跟着新格式更新。

## J. 数据保护

（放在最后做：下面会匿名化测试数据。）

先让 A 绑着一个测试 QQ（记作 QA，例如 `12345671`；用验证码或名单都行），下面的 `<A 的用户名>` 换成 A 在 AA 里的用户名。

- [ ] A 还有绑定时，运行 `python manage.py qqbot_erase --qq <QA> --user <A 的用户名> --dry-run`：被拒绝，提示仍有绑定并列出这个绑定，没有改动任何数据。
- [ ] A 解绑（或管理员强制解绑）后再运行同一条命令：显示会改动多少条记录，没有改动任何数据。「保留」里不会有 A；
      只有别的账号在这个 QQ 上有过记录时（例如另一个没用验证码就认领过它、后来被强制解绑的测试账号），才会列在「保留」里。
- [ ] （可选）只给 `--qq`、不给 `--user` 运行同样的试运行：A 的用户名这时会列在「保留」里，A 的记录不会被改动；这就是要同时给 `--user` 的原因。
- [ ] 去掉 `--dry-run`，输入 `yes`：「QQ 管理」→「操作记录」里关于 A 的记录（目标是 A，不只是 QA 上的）没有了 QQ 和对象，详情显示「个人数据已删除」；
      A 自己做的操作，操作者显示 `[erased]`，不是「机器人 / 系统」；别的账号在 QA 上的记录还在，QQ 和对象都没变。
